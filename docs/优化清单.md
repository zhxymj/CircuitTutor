# 开源项目化优化清单

> 目标：把当前仓库完善成"任何人克隆下来就能用、能跑测试、能贡献"的成熟开源项目。
> 本清单所有条目均基于**实测**，不含推测。基线审计日期：2026-10-21；按"陌生人 10 分钟建立信任"重排：2026-10-22。
>
> 排序原则：先让项目**真正存在于 GitHub 且可发布**，再让结论**可量化、可溯源**，然后降低**维护与贡献成本**，最后做体验与生态。
> 编号已重排，旧编号与新编号的对应关系见文末附录 B。

## 优先级定义

| 级别 | 含义 | 判断标准 |
|---|---|---|
| **P0 发布就绪** | 没有这些，项目不算"在 GitHub 上" | 能 clone、能跑、能发布、能下载 |
| **P1 可信度与安全** | 决定别人是否相信结论、默认是否安全 | 结论可复验、默认不暴露 |
| **P2 工程质量** | 决定能否持续维护与被贡献 | 测试可并行、模块可拆分、路径可移植 |
| **P3 体验与生态** | 决定能否被发现与长期使用 | 文档、分发、可访问性、社区入口 |

## P1 可信度与安全

### P1-1 建立 ERC 黄金集与误报/漏报基准

现状：33 条规则只有零散用例，没有"该报必报、不该报不报"的逐规则基准，也没有误报率/漏报率数字。

做法：

- 在 `tests/fixtures/erc/<rule_id>/` 下为每条规则准备正例与反例。
- 每条规则至少 1 个正例（必须命中）与 1 个反例（不得命中）；边界值单独成例。
- 输出逐规则的误报/漏报计数，作为基线写入文档。
- 新增规则必须同时提交 fixture，否则测试失败。

验收：33/33 条规则都有正反例；缺少 fixture 时 `--profile fast` 直接失败；误报/漏报基线可复现。

### P1-2 统一门禁溯源证据格式

现状："未运行 = 未完成"的原则已经成立，但各门禁的输出格式不统一，证据里没有工具版本与输入哈希。

做法：

- 定义统一字段：`tool`、`version`、`command`、`input_sha256`、`started_at_utc`、`status`、`output_sha256`。
- 校验、导出、审计 JSON 共用同一结构。
- 前端在门禁结果旁展示工具版本与执行时间。

验收：任一"通过"结论可以只凭记录复验；未运行的工具在任何界面都不会显示为通过。

### P1-3 明确生成复现边界并提供离线 replay

现状：trace 有 `request_id`，但没有 prompt 与响应哈希；在线模型输出天然不可复现。

做法：

- trace 记录模型名、参数、`prompt_hash`、`response_hash`。
- 提供离线 replay：用录制的响应重跑确定性门禁，断网也能复验结论。
- 文档明确切分"生成非确定 / 门禁确定"。

验收：断网环境下，同一 trace 能复验出门禁结论；文档不再暗示"模型输出可复现"。

### P1-4 修正 `.env.template` 安全默认值

现状：`core/config.py` 默认 `LSQC_HOST=127.0.0.1`，README 与 SECURITY 均声明"默认仅本地"，但 [.env.template](../.env.template) 写的是 `0.0.0.0`。新手 `cp .env.template .env` 后直接运行 `python server.py`，服务会向局域网暴露（`start_demo.ps1` 会强制回本机，直接跑 server 不会）。

做法：

- 模板默认改为 `127.0.0.1`，注释写明"需要局域网访问时自行改为 0.0.0.0 并承担风险"。
- Docker 场景由 `docker-compose.yml` 单独显式设置 `0.0.0.0`。
- 增加测试：解析 `.env.template` 与 README 配置表，与 `core/config.py` 默认值逐项对齐。

验收：模板、代码、README、SECURITY 四处一致；漂移会被测试拦住。

### P1-5 增加并发上限与图片上传防护

现状：`ThreadingHTTPServer` 没有全局并发上限，LLM 最长 30 秒等待可能耗尽线程；图片接口放宽到 10 MB，但没有像素上限。

做法：

- 有界信号量或任务队列，超过上限返回 503 并说明原因。
- 图片解码前限制像素总量，做类型嗅探，拒绝伪装文件。
- 保持现有每 IP 限流不变。

验收：并发压测不会耗尽线程；超限请求返回明确状态码；畸形图片被拒绝且不崩溃。

### P1-6 锁死 `manufacturing_release=false` 边界

现状：该字段已是约定，但需要确保没有任何 API、导出器或前端开关能覆盖它。

做法：

- 导出层硬编码为 `false`，不读取请求参数。
- 前端不提供"发布制造"开关。
- 加回归测试：构造试图覆盖的请求，结果仍为 `false`。

验收：所有导出文件中该字段恒为 `false`；覆盖尝试被测试拦住。

## P2 工程质量

### P2-2 隔离测试产物，消除并行假失败

现状：[test_pipeline.py:335](../tests/test_pipeline.py#L335) 固定写 `tests/erc_results.json` 与 `frontend_manifest.json`，供前端测试消费。文件虽已被 `.gitignore` 覆盖，但两个 runner 并行时会争用同一路径——2026-10-21 实测出现 `PermissionError: [Errno 13]` 与 4 个假失败。

做法：输出改到 `tempfile.mkdtemp()` 或按进程 ID 命名的路径，通过环境变量传给消费方；文件锁是次选方案。

验收：两个 runner 并行跑 `--profile fast` 不再冲突；可在 CI 并行 job 中验证。

### P2-3 拆分 `server.py`

现状：1740 行，约 33 条 API 路由，路由分发、静态服务、业务 handler、限流与 SSE 混在一起。

做法：按域拆为 `api/`（generate、validate、spice、pcb、import、history…），`server.py` 只保留 HTTP 骨架与路由表。

约束：这是重构，需逐域搬移并保持路由与响应不变；每搬一个域跑一次 `--profile fast` + `--profile integration`。

验收：路由清单与重构前逐条一致；相关测试全绿。

### P2-4 拆分超长函数（9 个 ≥120 行）

最长的几处（2026-10-21 审计）：

| 位置 | 行数 |
|---|---|
| `core/llm.py:1174 generate_circuit_json()` | 195 |
| `core/pcb_manufacturing.py:204 run_manufacturing_pipeline()` | 194 |
| `core/llm.py:469 chat()` | 140 |
| `server.py:1554 _run_pipeline()` | 133 |
| `core/design_rules.py:557 engineering_notes()` | 133 |

建议优先拆 `generate_circuit_json()` 与 `run_manufacturing_pipeline()`：按"准备参数 / 执行 / 组装结果"切段，纯搬移不改行为。

验收：单个函数 ≤120 行；对应套件全绿。

### P2-5 清除数据里的本机绝对路径

`data/pcb_examples/manifest.json` 有 **450 处** `D:\` / `C:\Users` 路径，另有多份 run manifest 各 36–38 处。换机器即失效，且泄露本地目录结构。

修法：生成端改为相对仓库根的路径，或用占位符并加解析函数；已入库的历史 manifest 批量改写。

验收：跟踪文件中 `C:\Users` / `D:\智绘电路` 出现次数为 0；相关测试仍通过。

### P2-6 建立大电路性能基线（可选）

现状：没有大电路（500+ 元件）的渲染、命中测试与撤销栈基准。

做法：补一个可重复的基准脚本，记录渲染耗时、交互响应与内存占用；先本地跑，不阻塞 CI。

验收：基准脚本可重复执行，回归超出阈值时有报告。
